## Почему имена в коде — английские (а доки — русские)?

Это не баг, это профессия. Ключевые слова Java (`class`, `if`, `while`) — английские,
весь мировой код, библиотеки и собеседования — на английском. Если назвать метод
`заправитьРакету`, сломается половина инструментов, а резюме с таким кодом вызовет
вопросы. Поэтому правило проекта простое:

- **идентификаторы** (классы, методы, переменные) — всегда английский;
- **всё человеческое** (игра, ошибки, доки, учебные материалы) — русский.

Через месяц ты перестанешь замечать английский в коде — проверено на тысячах
студентов. А короткие английские комментарии в коде — твой ежедневный тренажёр чтения.

## static — «общее имущество корабля»

🚀 Всё, что помечено `static`, принадлежит **классу**, а не конкретному объекту.
Одна копия на всех. Представь устав корабля: он один, висит на стене, а не лежит
в кармане у каждого матроса.

🔍 Где в проекте: `ProbabilityCalculator` (статические методы + приватный конструктор —
это классическая **утилита**, как `java.util.Collections`), `MissionValidator.validateForLaunch`,
константы `GameConfig` (`public static final`), хелперы `MenuIO`.

Статические методы не видят `this` и нестатические поля — им просто не к кому обращаться:
какой именно объект ты имеешь в виду? Все одинаковые? Вот именно.

🪤 Ловушка: изменяемое статическое поле (`public static List...`) — это глобальная помойка:
состояние течёт между тестами, потоками и запусками. В проекте глобальным оставили только
**константы** — единственное легитимное исключение.

🎤 *«Что такое static в Java?»*
<details><summary>Ответ</summary>
Член класса, а не экземпляра: одна копия на всех. Статические методы не имеют доступа
к <code>this</code>/нестатическим полям. Применения: утилиты, константы, фабрики.
Злоупотребление (особенно mutable static) — скрытое глобальное состояние, боль в тестах
и многопоточности.
</details>

## final — «запечатано капитаном»

🚀 У `final` три лица, и все про **запрет изменений**:
- переменная — ссылку нельзя переназначить (сам объект меняться может!);
- метод — нельзя переопределить;
- класс — нельзя наследовать (как `String`).

🔍 Где в проекте: `Transaction` и `LaunchRecord` — неизменяемые классы, все поля `final`;
`MissionResult` — это `record` (неизменяемость из коробки); `GameConfig` — константы;
`Employee.MIN_SKILL/MAX_SKILL` — границы, которые физически нельзя сдвинуть.

🪤 Ловушка: `final List<String> list` — список менять **можно** (`add` работает!),
нельзя только присвоить `list = другойСписок`. `final` запечатывает стрелку, а не дом.

🎤 *«Что значит final для переменной, метода и класса?»*
<details><summary>Ответ</summary>
Переменная: однократное присваивание. Метод: запрет override. Класс: запрет extends.
<code>final</code> — основа immutability и потокобезопасности: неизменяемым объектом
можно делиться между потоками без синхронизации.
</details>

## this / super / конструкторы — «кто я и откуда»

🚀 `this` — «я сам» (текущий объект). `super` — «мой родитель». Конструктор —
первый приказ при рождении объекта: пока он не отработал, объекта как бы нет.

🔍 Где в проекте: `Rocket.setName` — `this.name = ...` (разруливает конфликт имён
параметра и поля); `Engineer(...)` → `super(...)` (родитель инициализирует общее);
`Company` — два **перегруженных** конструктора, короткий вызывает длинный через `this(...)`
(**chaining**); `Employee.train()` / `train(int)` — перегрузка.

🪤 Ловушка: вызов `super(...)` обязан быть **первой строкой** конструктора.
Забыл — Java вставит `super()` сама, а если у родителя нет конструктора без аргументов —
получишь ошибку компиляции. В `quests/Quest02_Pilot.java` есть эксперимент, где ты
ломаешь это специально, чтобы запомнить навсегда.

🎤 *«Чем this отличается от super? Что такое constructor chaining?»*
<details><summary>Ответ</summary>
<code>this</code> — текущий экземпляр (поля, методы, вызов другого конструктора этого же класса).
<code>super</code> — доступ к родителю (его конструктор/методы/поля). Chaining — конструкторы
вызывают друг друга, чтобы логика инициализации жила в одном месте.
</details>

## Методы: параметры, return и область видимости — «приказы с подписью»

🚀 Параметры — копии (см. pass-by-value!). `void` ничего не возвращает.
Early return убивает вложенность: нашёл ответ — вернул, дальше не читаем.
Переменная живёт в `{ }`, где объявлена: счётчик — ДО цикла, `i` — только внутри.
Тернарник `? :` — if/else в одно выражение (не вкладывай больше двух уровней!).

🔍 Где в проекте: `firstPositive`-идея — в любом поисковике репозиториев;
early return — в `MissionValidator` (каждая проверка сразу бросает);
перегрузки `createMission` — три тёзки в `MissionService`.

🪤 Ловушка: использовать переменную цикла ПОСЛЕ цикла — не скомпилируется.
Лекарство: объявить аккумулятор до цикла.

🎤 *«Что такое early return и зачем?»*
<details><summary>Ответ</summary>
Возврат из метода сразу при нахождении ответа/ошибки вместо флагов и глубокой
вложенности. Код читается сверху вниз как список случаев, цикломатическая
сложность падает.
</details>

## Модификаторы доступа — «уровни допуска»

🚀 `private` (только свой класс) → без слова = package-private (весь пакет!) →
`protected` (пакет + наследники) → `public` (все). Главная ошибка: думать, что
«без слова» = private. Нет — это пакет! Поля — почти всегда `private` + геттеры;
конструктор `protected` — только для наследников (как у `Employee`).

🔍 Где в проекте: все поля домена — `private`; `protected Employee(...)` зовут
`Pilot/Engineer/...`; package-private методы ищи сам (разминка!).

🪤 Ловушка: забыл модификатор у «внутреннего» метода — он виден всему пакету.
Инкапсуляция начинается с минимально возможного доступа.

🎤 *«Дефолтный модификатор в Java?»*
<details><summary>Ответ</summary>
Package-private: видно внутри пакета. Отличие от private (только класс),
protected (+наследники вне пакета) и public (все).
</details>

## Примитивы vs ссылки / стек vs куча — «карта и территория»

🚀 Примитив (`int`, `double`, `boolean`...) — это само значение, лежит прямо в переменной.
Ссылка — это **адрес** объекта, который живёт в куче (heap). Переменная со ссылкой —
как записка «ракета в ангаре №3»: порвал записку — ракета цела, ангар никуда не делся.

🔍 Где в проекте: `Rocket.fuel` (`int` — копируется по значению) vs `Rocket.model`
(ссылка на общий `RocketModel` — один на всех). Метод `refuel(int amount)`: сколько ни
прибавляй к параметру внутри — снаружи ничего не изменится, потому что внутрь прилетела **копия**.

А вот `damage(int amount)` меняет поле объекта — потому что копия ссылки всё равно
ведёт на тот же объект. Метод получает копию стрелки, но дом — общий.

🪤 Ловушка: `==` для объектов сравнивает **стрелки**, а не дома. Два одинаковых
`new Rocket(...)` с `==` — `false`. Для содержимого — только `equals`.

🎤 *«Где живут примитивы и объекты? Что происходит при передаче объекта в метод?»*
<details><summary>Ответ</summary>
Примитивы — по значению (часто на стеке). Объекты — в куче, в переменных лежат ссылки.
В Java передача ВСЕГДА по значению: для объектов копируется ссылка. Следствие: поля менять
можно, а подменить сам объект у вызывающего — нет. Стек хранит кадры вызовов и локальные
переменные; куча — объекты; сборщик мусора чистит только кучу.
</details>

## Карта памяти: стек, куча, null и корни GC — «план помещений»

🚀 Стек: кадры вызовов + локальные переменные (умер метод — умер кадр).
Куча: все объекты. Переменная-объект — стрелка; две стрелки могут вести
в один дом. `null` = «стрелка в никуда» (рвёт только свою, объект жив, пока
его держит хоть кто-то). Жив = достижим от корней: стек потоков, static-поля,
JNI-ссылки. `obj = null` лишь рвёт стрелку, удаления может не быть вообще;
`System.gc()` — просьба, а не приказ, полагаться нельзя.

🔍 Где в проекте: `Mission.crewIds` хранит id, а не ссылки — объекты экипажа
живут в репозитории; `resolveCrew` достаёт их по стрелкам-id.

🪤 Ловушка: «занулил — память освободилась». Нет: освободит GC, когда дойдёт,
если объект правда недостижим.

🎤 *«Что такое GC roots?»*
<details><summary>Ответ</summary>
Точки, от которых GC считает достижимость: локальные переменные и параметры
в стеках потоков, static-поля классов, JNI-ссылки. Недостижимое — мусор.
</details>

## Целочисленная арифметика: деление, %, overflow, кастинг — «минное поле»

🚀 `7/2==3` (дробь отбрасывается!), `-7%3==-1` (знак остатка = знак делимого),
`MAX_VALUE+1==MIN_VALUE` (заворот по кругу, исключения нет!),
`(int)2.9==2` (отброс, не округление), `i++` отдаёт старое, `++i` — новое.
`&&`/`||` ленивые (short-circuit): `x != null && x.foo()` безопасно.

🔍 Где в проекте: `MoneyUtils.parse` чистит ввод; целочисленные ловушки —
в `Quest07_Arrays`, секция A (любимое собеседований!).

🪤 Ловушка: среднее `sum / length` в int'ах — сначала поделись, потом удивляйся.
Лекарство: `(double) sum / length`.

🎤 *«Что будет при переполнении int?»*
<details><summary>Ответ</summary>
Ничего не будет — молча завернётся по модулю 2³² (дополнение до двух).
Проверки переполнения — вручную (`Math.addExact` бросает исключение!).
</details>

## String, пул строк, неизменяемость — «гравировка по металлу»

🚀 `String` неизменяем: любая «модификация» (`strip()`, `toUpperCase()`, `+`) создаёт
**новую** строку. Как гравировка: ошибся буквой — бери новую пластину.
Зато строки можно безопасно делить между потоками и кешировать `hashCode`.

Пул строк: литералы (`"Союз"`) Java складывает в общий пул и переиспользует.
Поэтому `"Союз" == "Союз"` — `true` (одна пластина!), а `new String("Союз") == "Союз"` — `false`.

🔍 Где в проекте: `InputReader` (`strip()`, `toLowerCase()`, парсинг чисел);
`SaveLoadService.escape/unescape/split` — посимвольная обработка;
`StringBuilder` в `MissionService` (бортовой журнал), `StatisticsService.buildReport`,
`FinanceService.balanceSummary`; `String.formatted` — везде для отчетов.

Почему `StringBuilder` в циклах: `result = result + кусок` в цикле на 10 000 итераций
создаёт 10 000 промежуточных строк-мусора. `StringBuilder` дописывает в один буфер.
Одиночные `formatted` — нормально, там цикла нет.

🪤 Ловушка: сравнение строк через `==` работает **иногда** (пул!) — самый коварный
«иногда-баг» в Java. Правило: содержимое — только `equals`. В `quests/Quest03_Engineer.java`
(LVL-21) эта ловушка стоит первой.

🎤 *«Почему String immutable? Что такое String pool? == vs equals?»*
<details><summary>Ответ</summary>
Неизменяемость даёт: безопасность в многопоточке, кеширование hashCode, возможность пула,
безопасность (имя класса/путь к файлу нельзя подменить). Пул: литералы и intern()-строки
переиспользуются. <code>==</code> — идентичность ссылок, <code>equals</code> — равенство
содержимого. Строки всегда сравниваем через equals.
</details>

## Строки в бою: методы и live-coding приёмы — «ножевой бой»

🚀 Рабочий набор: `length`, `charAt`, `substring(from, to)` (to — НЕ включительно!),
`indexOf` (+ перегрузка с fromIndex), `replace/replaceAll` (`\d` — уже почти regex),
`split("\\s+")` (пустые ХВОСТЫ отбрасываются!), `strip`, `toLowerCase`,
`startsWith/endsWith/contains`, `String.join`, `StringJoiner` (префикс+суффикс).
Приёмы live-coding: разворот через `StringBuilder.reverse`, палиндром = равен
развороту, анаграммы = сортировка массивов символов, частота = счётчик/карта,
первый уникальный = два прохода, дубликаты = `indexOf==-1` значит «не было».

🔍 Где в проекте: `SaveLoadService.escape/unescape/split` — ручной парсинг;
`InputReader` — strip/parse; `Quest13_Strings` — 15 задач.

🪤 Ловушка: `split(",")` на `"a,"` даст `["a"]` — хвост съеден. Нужны пустые —
`split(",", -1)`.

🎤 *«Как проверить анаграммы?»*
<details><summary>Ответ</summary>
Привести к одному регистру, отсортировать массивы символов, сравнить через
`Arrays.equals`. O(n log n), понятно, коротко. O(n)-вариант — карта частот.
</details>

## Regex для AQA: Pattern, Matcher, группы — «сито для логов»

🚀 Regex в AQA — разбор логов, проверка ID, значения из ответов API.
Минимум: `String.matches` (ВСЯ строка!), `Pattern.compile + matcher.find`
(искать внутри), группы `()` + `group(1)`, классы `\d \w \s`, квантификаторы
`+ * ? {2}`, точка = «любой символ» (экранируй `\\.`!). В Java-строке каждый
бэкслэш удваивается: regex `\d` пишется `"\\d"`.

🔍 Где в проекте: `Quest14_Regex` — ID, email, числа из строки, уровень лога,
значение из JSON-крошки. В проде regex уже был: `replaceAll("\\d", ...)`!

🪤 Ловушка: `matches` vs `find` — первая требует всю строку, вторая ищет кусок.
Путаница = вечнозелёный/вечнокрасный тест.

🎤 *«Как вытащить значение из строки лога?»*
<details><summary>Ответ</summary>
Скомпилировать `Pattern` со скобочной группой, `matcher.find()`,
забрать `group(1)`. Pattern компилировать один раз (дорого!), Matcher — лёгкий.
</details>

## Неизменяемость на практике: final-ссылки и defensive copy — «сейф»

🚀 `final` держит стрелку, не дом: `final List` можно `add`, нельзя `=`.
Настоящий immutable: все поля `private final` + нет сеттеров + коллекции
копируются НА ВХОДЕ (`new ArrayList<>(...)` — чужой список потом поменяют!)
и НА ВЫХОДЕ (иначе допишут через геттер!). «Изменение» = новый объект
(`withThrust` возвращает копию). `record` — тот же идеал из коробки,
но коллекцию внутри record'а тоже надо копировать!

🔍 Где в проекте: `Transaction`, `LaunchRecord`, `MissionResult` — immutable;
`Company.getTransactions()` отдаёт `unmodifiableList` (вид, а не копия!).

🪤 Ловушка: `unmodifiableList` vs `copyOf` — первая видит чужие изменения
оригинала, вторая — снимок. Для сейфов бери копию.

🎤 *«Как сделать класс неизменяемым?»*
<details><summary>Ответ</summary>
final-класс, все поля private final, инициализация в конструкторе, нет сеттеров,
defensive copy мутабельных полей на входе и выходе, equals/hashCode по полям.
</details>

## == vs equals / контракт equals-hashCode — «паспортный контроль»

🚀 `==` спрашивает: «это один и тот же объект?». `equals` спрашивает: «это тот же
самый корабль по сути?». У каждой сущности проекта есть «паспорт» — `UUID id`:
две записи с одним `id` — одна и та же ракета, даже если у одной топливо старое
(устаревшая копия), а имя в другой опечатано.

**Контракт** (закон, а не рекомендация): равные объекты обязаны иметь равные
`hashCode`. Нарушил — `HashSet` начнёт плодить дубликаты, а `HashMap` терять ключи,
причём молча и через раз. Самый тихий убийца в Java.

🔍 Где в проекте: `Rocket`, `Employee`, `Mission`, `Transaction`, `LaunchRecord`
равны по `id`; `Company` — по имени без учёта регистра (и `hashCode` честно считает
от нижнего регистра — иначе контракт рухнет). Покрыто тестами `DomainEqualityTest`.

🪤 Ловушка: переопределил `equals`, забыл `hashCode` — IDE даже предупредит, а код
скомпилируется. Падать будет в проде, в `HashSet`, в пятницу вечером.

🎤 *«Что будет, если переопределить equals без hashCode?»*
<details><summary>Ответ</summary>
Нарушится контракт: равные объекты разъедутся по разным бакетам HashMap/HashSet.
Следствия: дубликаты в сете, <code>get()</code> возвращает null для существующего ключа.
Правило: всегда генерируй пару вместе; поля в обоих методах — одни и те же.
</details>

## Коллекции: List / Set / Map (+ concurrent) — «отсеки корабля»

🚀 У каждого отсека своё назначение:
- **`List`** — склад с полками по номерам: порядок важен, дубликаты можно
  (`ArrayList` — быстро читать по индексу, дорого вставлять в середину).
- **`Set`** — шлюз с фейсконтролем: дубликаты не проходят. `LinkedHashSet` ещё и
  помнит порядок прихода.
- **`Map`** — картотека: «ключ → значение», поиск за O(1) в среднем.
- **`ConcurrentHashMap`** — картотека, которую могут читать/писать несколько
  потоков без общей очереди.

🔍 Где в проекте:
- `List<Transaction>` / `List<LaunchRecord>` в `Company` — история, порядок важен
  (`ArrayList`, обёрнут в `synchronizedList`, потому что фоновые полёты дописывают историю);
- `Set<UUID> crew` в `Mission` (`LinkedHashSet`: один человек — один раз + стабильный порядок);
- `Map<MissionStatus, Long>` в `missionsByStatus` (группировка);
- `ConcurrentHashMap` в `InMemory*Repository` (полёты из разных потоков читают состояние);
- `EnumMap`/`EnumSet` в `MissionValidator` (самые быстрые контейнеры для enum-ключей).

🪤 Ловушка 1: `HashMap` **не** потокобезопасен — гонка при записи может потерять данные
или вообще зациклить чтение (в старых JDK). Для потоков — `ConcurrentHashMap`.
Ловушка 2: мутировать объект-ключ после `put` (поменял поле, участвующее в `hashCode`) —
ключ «потеряется» в чужой корзине. Поэтому ключи — immutable.

🎤 *«ArrayList vs LinkedList? Как устроен HashMap? Чем ConcurrentHashMap лучше synchronizedMap?»*
<details><summary>Ответ</summary>
ArrayList — массив: O(1) доступ, вставка в середину O(n). LinkedList — узлы: дёшево по краям,
медленно по индексу. HashMap: массив корзин по hashCode, коллизии — список/дерево (при &gt;8),
resize с рехешированием. ConcurrentHashMap: lock-free чтения, блокировки на уровне корзин
при записи + атомарные методы (computeIfAbsent) — масштабируется, в отличие от одной
блокировки на всю карту у synchronizedMap/Hashtable.
</details>

## Иерархия коллекций и выбор структуры — «выбирай оружие»

🚀 Вопросы выбора (именно их задают!): нужны дубликаты? важен порядок? нужна
сортировка? нужны пары ключ-значение? очередь? Уникальность+скорость → Set;
порядок+индекс → List; пары → Map; FIFO/стек → Deque; минимум первым → PriorityQueue.
Интерфейсы (`List/Set/Map`) — тип переменных, реализации — после `new`.

🔍 Где в проекте: `Set<UUID> crewIds` (уникальность!), `Map<UUID, Mission>` (поиск по id),
`List<Transaction>` (порядок истории!). Каждое решение осознанное.

🪤 Ловушка: поле типа `ArrayList` вместо `List` — прибиваешь себя к реализации.
Программируй на интерфейсах!

🎤 *«Какую коллекцию для уникальных посетителей по порядку прихода?»*
<details><summary>Ответ</summary>
`LinkedHashSet`: уникальность хэш-сета + порядок вставки. Нужна сортировка —
`TreeSet`. Только скорость — `HashSet`.
</details>

## ArrayList и LinkedList изнутри — «массив против цепочки»

🚀 ArrayList = массив с запасом: `get/set` — O(1), вставка в середину — O(n)
со сдвигом, рост — новый массив ×1.5 + копирование (`size` vs `capacity`!).
LinkedList = цепочка узлов: дёшево по краям (как Deque), но `get(i)` идёт
по ссылкам — O(n). Ловушка «LinkedList всегда быстрее при вставке» — ложь:
вставка в середину требует сначала ДОЙТИ до места (O(n) на проход!).

🔍 Где в проекте: везде `ArrayList` (истории, результаты) — доступ и добавление
в конец; `LinkedList` — только там, где Deque-операции (`Quest15`, B1).

🪤 Ловушка собеседований: «когда LinkedList реально лучше?» — очередь/стек
с частыми операциями на концах... хотя и там `ArrayDeque` обычно быстрее!

🎤 *«Сложность get/add/remove у ArrayList?»*
<details><summary>Ответ</summary>
get/set — O(1); add в конец — O(1) амортизированно (иногда resize O(n));
вставка/удаление в середине — O(n) из-за сдвига. resize: новый массив
в полтора раза больше + `Arrays.copyOf`.
</details>

## HashMap изнутри: корзина, рост, null'ы — «картотека с секретом»

🚀 Путь ключа: `hashCode → hash → номер корзины → цепочка/дерево → equals`.
Коллизия — норма: несколько ключей в одной корзине, ищет `equals`.
`capacity 16`, `load factor 0.75`: переполнение → resize ×2 с рехешированием
(дорого! задавай capacity заранее, если знаешь размер). С 8+ в корзине —
treeification (дерево вместо списка, Java 8+). null-ключ: HashMap — можно (один!),
TreeMap/ConcurrentHashMap — нельзя. Ключ — immutable, иначе «уплывёт»!

🔍 Где в проекте: все `InMemory*Repository` — `ConcurrentHashMap`;
`missionsByStatus` — `groupingBy` строит `HashMap`.

🪤 Ловушка: `get` вернул null — ключа нет ИЛИ значение null? Различай
`containsKey`! Вторая: мутабельный ключ (см. Quest16, задача 4).

🎤 *«Что происходит при коллизии?»*
<details><summary>Ответ</summary>
Ключи с одинаковым хэшем лежат в одной корзине списком (или красно-чёрным
деревом при 8+). Поиск: корзина по хэшу, дальше линейный проход с `equals`.
Поэтому `equals` обязан согласовываться с `hashCode`.
</details>

## Comparable и Comparator — «кто первый»

🚀 Natural ordering (`Comparable`, один на класс: `compareTo`) — «естественный»
порядок типа. `Comparator` — внешние правила, сколько угодно: лямбдой,
`comparingInt`, цепочки `thenComparing` (второй критерий при равенстве!).
`reversed()` переворачивает ВСЮ цепочку. `nullsFirst/Last` — null'ы без NPE.
Сортировка в Java стабильна: равные сохраняют исходный порядок.

🔍 Где в проекте: `sortByReliabilityDesc`, `topEarners` (sorted+limit),
`findBestEmployee` (max по компаратору) — живые цепочки!

🪤 Ловушка: `Comparator` должен быть согласованным (транзитивность!), иначе
сортировка сойдёт с ума молча. И никогда `a - b` для int (переполнение!) —
только `Integer.compare`.

🎤 *«Comparable vs Comparator?»*
<details><summary>Ответ</summary>
Comparable — естественный порядок, зашит в класс, один. Comparator — внешнее
правило, их много, для сортировок «по-разному». `compareTo` возвращает
отрицательное/ноль/положительное, контракт: согласованность с equals желательна.
</details>

## Iterator и ConcurrentModificationException — «не пили сук»

🚀 for-each прячет итератор (`hasNext/next`), но коллекция считает модификации
(`modCount`): удаление в цикле — CME! Лечение — `iterator.remove()`
(единственное легальное удаление на ходу). `ListIterator` умеет ещё и назад/вставку.
Правило AQA: видишь `remove` в for-each — ставь на CME.

🔍 Где в проекте: `Quest15`, D1 (увидеть CME!) → D2 (починить итератором).

🪤 Ловушка: CME — не про потоки! Это защита от изменения во время обхода
хоть в одном потоке. Многопоточные коллекции — отдельная история.

🎤 *«Почему CME и как чинить?»*
<details><summary>Ответ</summary>
Fail-fast итераторы сверяют modCount коллекции с ожидаемым; расхождение —
значит, структуру меняли мимо итератора. Чинится `iterator.remove()`,
либо сбором «на удаление» + `removeAll` после цикла, либо `removeIf`.
</details>

## Collections-утилиты и честная неизменяемость — «швейцарский нож»

🚀 `Collections.sort/reverse/shuffle/min/max/frequency`, `removeIf`,
`List.of/Set.of/Map.of` — короткие НЕИЗМЕНЯЕМЫЕ фабрики (любой `add` — UOE!).
`unmodifiableList` — вид-обёртка (видит чужие правки оригинала!),
`List.copyOf` — независимый снимок. Для сейфов — копия.

🔍 Где в проекте: `Company.getTransactions()` — `unmodifiableList`;
`requiredRolesFor` — `Set.copyOf`.

🪤 Ловушка: обернул список в unmodifiable, а оригинал поменял кто-то другой —
«неизменяемость» протекла. Читай контракт, а не название!

🎤 *«copyOf vs unmodifiableList?»*
<details><summary>Ответ</summary>
`copyOf` — независимая копия-снимок (null запрещён!). `unmodifiableList` —
только вид: менять через него нельзя, но изменения оригинала видны.
</details>

## interface vs abstract class — «должность vs родство»

🚀 Правило корабля:
- **interface** = «умеет делать» (должность). Пилот и инженер оба «умеют летать в экипаже»,
  но родственниками не являются.
- **abstract class** = «является + общее наследство» (родство): у всех сотрудников есть
  id, имя, зарплата — это общее **состояние**, а состояние интерфейсы хранить не умеют.

🔍 Где в проекте: `GameEvent` — интерфейс (6 неродственных реализаций: от погоды до
инвесторов; новую прикручиваешь, не трогая чужой код — Open/Closed без фреймворков);
`Repository<T,ID>` — интерфейс-контракт хранилища. `Employee` — абстрактный класс:
общие поля + конструктор + часть поведения, а `getRole()/getMissionBonus()` —
абстрактные, каждый подвид решает сам.

С Java 8 у интерфейсов есть `default`-методы, но полей состояния — по-прежнему нет.
Поэтому выбор простой: нужно общее состояние → abstract class; нужна способность → interface.

🪤 Ловушка: «сделаю всё интерфейсами с default-методами» — получишь дублирование полей
в каждом классе и невозможность общей инициализации в конструкторе.

🎤 *«Когда abstract class, а когда interface?»*
<details><summary>Ответ</summary>
Abstract class — общее состояние и шаблонное поведение («is-a»). Interface — контракт
способностей («can-do»), множественная реализация. Наследовать класс можно один,
интерфейсов — сколько угодно. Пример из проекта: Employee — abstract (поля!),
GameEvent — interface (только поведение).
</details>

## Enum на практике — «конечный список»

🚀 Enum — класс с фиксированным набором объектов: поля, конструктор (неявно
private!), методы, `values()`, `valueOf()` (мусор — `IllegalArgumentException`!),
switch без префикса (`case PILOT`, не `case EmployeeRole.PILOT`).
Вершина — enum с ПОВЕДЕНИЕМ: каждая константа переопределяет метод
(анонимный подкласс!). Добавить константу = добавить поведение, switch'и
чинить не надо. `ordinal()` в логике — табу (порядок хрупок!).

🔍 Где в проекте: `MissionType`, `RocketModel` — поля+конструктор+методы;
`MissionStatus.isTerminal()` — поведение; `REQUIRED_ROLES` — `EnumMap/EnumSet`.

🪤 Ловушка: `==` для enum — МОЖНО и нужно (константы синглтоны, null-безопасно
слева... нет! `null == X` — false без NPE, а вот `x.equals` на null упадёт).

🎤 *«Чем enum с поведением лучше switch?»*
<details><summary>Ответ</summary>
Полиморфизм вместо ветвления: новая константа несёт своё поведение сразу,
switch для неё писать/править не надо, забыть ветку невозможно (компилятор
заставит реализовать abstract-метод).
</details>

## Overload vs Override — «тёзки vs наследники»

🚀 **Overload** (перегрузка): одно имя, разные параметры — решается **компилятором**
(раннее связывание). **Override** (переопределение): тот же метод у наследника —
решается **в рантайме** по реальному объекту (позднее связывание, полиморфизм).

🔍 Где в проекте. Override: `Engineer.work()` vs `Employee.work()`, `getRole()`,
`getMissionBonus()` — у всех четырёх профессий свои версии. Overload: `Rocket.refuel()` /
`refuel(int)`, `Employee.train()` / `train(int)`, два `calculateSuccessProbability`.

🪤 Ловушка: чуть-чуть не та сигнатура (например, `equals(Rocket o)` вместо
`equals(Object o)`) — и вместо override получился overload: метод есть, а полиморфизма
нет. Лекарство — аннотация `@Override`: компилятор закричит, если переопределять нечего.

🎤 *«Что сломается, если забыть @Override?»*
<details><summary>Ответ</summary>
Ничего не сломается — в этом и ужас: код скомпилируется, но вместо переопределения
создастся новый метод (overload), и полиморфный вызов пойдёт в родительскую версию.
<code>@Override</code> превращает молчаливый баг в ошибку компиляции.
</details>

## Исключения: checked vs unchecked / try-finally / try-with-resources

🚀 Два племени:
- **Unchecked** (`RuntimeException`): «ты сам виноват» — нарушение бизнес-правил, которое
  предотвращается проверками. Компилятор не заставляет ловить.
- **Checked** (`Exception`): «случилась беда извне» — диск, сеть, кривой файл. Компилятор
  **заставляет** обработать: или `catch`, или `throws` в сигнатуре.

🔍 Где в проекте:
- Unchecked: `InsufficientFundsException`, `RocketNotReadyException`,
  `MissionValidationException`, `EmployeeNotAvailableException` (все — наследники общего
  `SpaceCompanyException`). Меню ловит их пачкой на границе UI — одна `catch` на пункт меню.
- Checked: `GameSaveException` — обёртка над `IOException` и кривыми данными.
- `try/finally` там, где оправдан: `MissionService.flyMission` — если полёт рухнул
  с неожиданной ошибкой, `finally` возвращает ракету и экипаж из `ON_MISSION`, иначе они
  застрянут в небе навсегда; `Application.run` — глушит пул потоков и закрывает ввод
  даже при падении меню.
- try-with-resources: чтение/запись сейва в `SaveLoadService`, `InputReader implements AutoCloseable`.

🪤 Ловушка 1: `catch (Exception e) {}` — пустой catch хоронит ошибку заживо: программа
«работает», данные гниют. Ловушка 2: checked-исключения на каждый чих — сигнатуры
тонут в `throws`, все начинают писать `throws Exception`. Баланс проекта: 4 unchecked
(бизнес) + 1 checked (среда).

🎤 *«Когда создавать checked-исключение? Что гарантирует finally?»*
<details><summary>Ответ</summary>
Checked — для восстановимых внешних сбоев, которые вызывающий не может предотвратить
валидацией (I/O, сеть). finally выполняется всегда (кроме System.exit и смерти JVM) —
идеален для освобождения ресурсов и отката состояний. try-with-resources — синтаксический
сахар над try-finally с close(), закрывает в обратном порядке открытия и подавляет
вторичные исключения корректно.
</details>

## Исключения вглубь: throw, всплытие, ресурсы — «пожарная тактика»

🚀 `throw` бросает, `throws` предупреждает (для checked — обязателен в сигнатуре!).
Непойманное всплывает по стеку до `main` и роняет программу — для багов нормально,
для бизнес-ситуаций ловят на границе (у нас — `ConsoleMenu`). Multi-catch:
`catch (A | B e)` — типы не должны наследоваться! Ресурсы закрываются в ОБРАТНОМ
порядке; бросают и тело, и `close` — наружу идёт исключение ТЕЛА, второе станет
`suppressed`-прицепом. Свой `AutoCloseable` — 5 строк.

🔍 Где в проекте: `Quest20_Exceptions` — все 8 задач, включая 3 ловушки return+finally.

🪤 Ловушка: `catch (Exception e) {}` пустой — хоронит ошибку заживо. И `return`
в `finally`, бьющий `return` в `try`, — пиши только на собеседовании, не в проде!

🎤 *«Что такое suppressed-исключения?»*
<details><summary>Ответ</summary>
Если в try-with-resources бросили и тело, и `close()`, наружу идёт исключение тела,
а второе цепляется через `addSuppressed` и видно в трейсе (`Throwable.getSuppressed`).
Данные не теряются.
</details>

## Generics — «чертежи вместо слепков»

🚀 Без generics репозиторий хранил бы `Object` — достаёшь ракету, а там каст
`(Rocket) ...` и молитва. С generics `Repository<Rocket, UUID>` компилятор сам следит:
положил не то — не скомпилируется. Один чертёж — много типов.

🔍 Где в проекте: `Repository<T, ID>` + три наследника; generic-метод
`MenuIO.<T>choose(...)` — один метод выбора для ракет, людей и миссий;
`List<? extends Employee>` в `ProbabilityCalculator` — **PECS**: метод только
*читает* сотрудников (producer → `extends`), поэтому принимает и `List<Pilot>`,
и `List<Engineer>`. Инвариантность (`List<Pilot>` — НЕ `List<Employee>`) однажды уже
ломала компиляцию тестов — чинилось именно wildcard'ом.

Стирание типов (erasure): в рантайме `<T>` испаряется — поэтому нельзя `new T()`,
`new T[10]` и `x instanceof T`. Обходные пути: `Class<T>` токены, фабрики, массивы
через `Array.newInstance`.

🪤 Ловушка: `List<String>` и `List<Integer>` в рантайме — один и тот же класс.
А `List<Object> objs = new ArrayList<String>()` — не компилируется (и правильно:
иначе туда можно было бы положить `Integer`).

🎤 *«Почему List&lt;String&gt; нельзя присвоить List&lt;Object&gt;? Что такое PECS?»*
<details><summary>Ответ</summary>
Generics инвариантны ради type-safety: иначе в список строк пролез бы Integer.
PECS (Producer Extends, Consumer Super): читаешь из структуры — <code>? extends T</code>,
пишешь в неё — <code>? super T</code>. Пример: <code>sort(List&lt;T&gt;)</code> читает и пишет —
без wildcard; метод «посчитай бонусы экипажа» только читает — <code>? extends Employee</code>.
</details>

## Generics вглубь: границы, PECS, стирание — «чертежи с допусками»

🚀 `<T extends Number>` — граница: внутри можно `doubleValue()`.
PECS: читаем — `? extends T` (producer), пишем — `? super T` (consumer);
классика `copy(src extends, dst super)`. Инвариантность: `List<Integer>`
НЕ `List<Number>` (иначе пролез бы `Double` и всё сломалось бы!).
Стирание: в рантайме `<T>` испаряется — нет `new T()`, `new T[]`,
`instanceof T` (обход: готовое значение, `Class<T>`-токен, `Array.newInstance`).

🔍 Где в проекте: `List<? extends Employee>` в калькуляторе (читаем!);
`MenuIO.<T>choose` — generic-метод; `Quest27_Generics` — 8 задач.

🪤 Ловушка: два метода `foo(List<String>)` + `foo(List<Integer>)` — НЕ скомпилируются:
после стирания сигнатуры одинаковые!

🎤 *«Почему нельзя new T()?»*
<details><summary>Ответ</summary>
Из-за стирания в рантайме неизвестно, что за T. Обходы: передать готовый
экземпляр/фабрику (`Supplier<T>`), `Class<T>` + `newInstance`, коллекции вместо
массивов. Массив `new T[]` — та же причина (массивы помнят тип!).
</details>

## Функциональные интерфейсы: четвёрка из java.util.function — «четыре лица»

🚀 Вся библиотека — 4 лица: `Predicate<T>` (проверка → boolean),
`Function<T,R>` (преобразование), `Consumer<T>` (потребить, void),
`Supplier<T>` (дать). Плюс `Bi*`-версии и примитивные (`IntPredicate` — без
боксинга!). Композиция: `andThen/compose` клеят функции в конвейер.
Свой интерфейс — аннотация `@FunctionalInterface` (компилятор следит за
«ровно один абстрактный метод»). Лямбда в цикле требует effectively-final
переменную — иначе не скомпилируется (защита от общего счётчика!).

🔍 Где в проекте: `filter` берёт Predicate, `map` — Function (везде в стримах);
`MenuIO.choose` — `Function<T, String>`; `Quest28_Functional` — 8 задач.

🪤 Ловушка: `Function` с побочками внутри `map` — конвейер врёт (ленивость +
повторы). Чистые функции — спокойный сон.

🎤 *«Что такое effectively final?»*
<details><summary>Ответ</summary>
Переменная, которой присваивают один раз (без слова final). Лямбда/анонимный
класс захватывают КОПИЮ значения — изменяемая переменная дала бы рассинхрон,
поэтому компилятор требует финал-по-факту.
</details>

## Лямбды / Stream API / Optional / method references — «конвейер»

🚀 Цикл говорит **как** делать (счётчик, индекс, аккумулятор). Стрим говорит **что**
получить: «зарплаты → больше 1000 → +10% → сумма». Короткие конвейеры читаются как
предложение, длинные — как скороговорка: тогда лучше обычный цикл. Проект держит оба
стиля сознательно — так и в проде, и на собеседованиях спрашивают оба.

🔍 Где в проекте:
- `totalIncome/totalExpenses`: `filter + map + reduce` — хрестоматийный конвейер;
- `missionsByStatus`: `groupingBy + counting` — одной строкой вместо 10 строк цикла;
- `sortByReliabilityDesc`, `topEarners(limit)`, `findMostExpensive(max)` — сортировки и поиски;
- method references: `Rocket::isReadyForLaunch`, `Employee::isAvailable`, `BigDecimal::add`;
- рядом — честные циклы: суммирование зарплат, подсчёт побед, `findByStatus` в репозиториях;
- `Optional` вместо `null`: все `findById`, `findMostExpensive`, `drawRandomEvent`,
  `ifPresentOrElse` в меню. Правило: «может отсутствовать» → `Optional`, а не `null` и не `-1`.

Ленивость: промежуточные операции (`filter`, `map`, `sorted`) ничего не делают —
конвейер запускается терминальной операцией (`toList`, `sum`, `collect`, `max`).
Без терминальной — тишина и пустота (классический баг новичка).

🪤 Ловушка 1: стрим можно пройти **один раз** — повторное использование бросает
`IllegalStateException`. Ловушка 2: `Optional.get()` без проверки — те же NPE, вид сбоку;
используй `orElse`, `ifPresent`, `map`.

🎤 *«Что такое функциональный интерфейс? Ленивые vs энергичные операции?»*
<details><summary>Ответ</summary>
Функциональный интерфейс — один абстрактный метод (Comparator, Function, Predicate,
свои). Лямбда — его краткая реализация. Промежуточные операции стрима ленивы
(строят план), терминальные — запускают выполнение. Параллельные стримы
(parallelStream) — только для CPU-тяжёлых независимых задач и без общего состояния.
</details>

## Stream API вглубь: коллекторы и лень — «конвейерный завод»

🚀 Промежуточные (`filter/map/flatMap/distinct/sorted/limit/skip/peek`) ленивы
и возвращают стрим; терминальные (`forEach/match/find/reduce/collect/count/sum`)
запускают всё. `flatMap` сплющивает (стрим стримов → плоский),
`peek` — только для отладки! Коллекторы: `toMap` (дубли ключей — взрыв, чинится
merge-функцией!), `groupingBy` + downstream (`counting/averaging`),
`partitioningBy` (всегда true/false), `joining`. Примитивные стримы
(`mapToInt`) — без боксинга + `sum/average`. Порядок важен: `filter` ДО `map`
считает меньше. Стрим одноразовый (второй терминал — ISE!).

🔍 Где в проекте: `missionsByStatus` (groupingBy+counting), `topEarners`
(sorted+limit), `totalIncome` (filter+map+reduce); `Quest18_Streams` — 17 задач + босс.

🪤 Ловушка: побочка в `map`/`forEach` с параллельным стримом — гонка.
Стримы — про преобразование, не про «сделать сбоку».

🎤 *«Intermediate vs terminal?»*
<details><summary>Ответ</summary>
Промежуточные ленивы и chainable (строят план), терминальные запускают
выполнение и дают результат/побочку. Без терминальной конвейер молчит —
классический баг новичка: «написал filter, ничего не произошло».
</details>

## Optional вглубь: ленивый дефолт и границы — «коробка с правилами»

🚀 `orElse` СТРОИТ аргумент всегда (даже когда не нужен!), `orElseGet(Supplier)` —
только при пустоте: дорогой дефолт — только через Get! Цепочки
`map/flatMap/filter/orElseThrow` вместо `isPresent`-лесенок.
НЕ надо Optional: в полях сущностей, в параметрах методов, в коллекциях
(`List<Optional>` — запах), для примитивов есть `OptionalInt/Double`.
`orElseThrow()` без аргументов бросает `NoSuchElementException`.

🔍 Где в проекте: `findById`, `findMostExpensive`, `drawRandomEvent`;
поле `assignedRocketId` — обычный nullable (и правильно!).

🪤 Ловушка: `optional.get()` без проверки — те же NPE, вид сбоку.
И `Optional.of(null)` — мгновенный NPE (для nullable есть `ofNullable`).

🎤 *«orElse vs orElseGet?»*
<details><summary>Ответ</summary>
`orElse` вычисляет аргумент всегда (даже при present — впустую),
`orElseGet` вызывает Supplier только при empty. Дорогие дефолты, исключения,
логирование — только через Get/Supplier-версию.
</details>

## java.time — «бортовые часы»

🚀 Старые `Date`/`Calendar` — изменяемые, потоконебезопасные, с месяцами от 0
(январь = 0, классика боли). `java.time` — immutable, потокобезопасные, человеческие:
`LocalDate`, `LocalDateTime`, `Duration`, `Period`.

🔍 Где в проекте: `createdAt/launchedAt/completedAt` миссий, `hireDate`/`foundedDate`,
симулированное время полёта `Duration` («1d 14h» в отчёте), ISO-8601 строки в сейвах
(`LocalDateTime.parse` обратно). Время в сейве — текст `2026-10-04T17:49:45.21` —
читаемо человеком и парсится без `SimpleDateFormat`.

🪤 Ловушка: `LocalDateTime` — без часового пояса («время на борту»). Для моментов,
которые сравнивают через часовые пояса/логи серверов, нужен `ZonedDateTime`/`Instant`.

🎤 *«Почему java.time лучше Date?»*
<details><summary>Ответ</summary>
Неизменяемость (потокобезопасность из коробки), понятный API (plusDays, between),
разделение понятий (дата / время / момент / длительность / период), отсутствие
мутабельных сюрпризов и месяцев-с-нуля.
</details>

## BigDecimal: деньги без магии — «копейка рубль бережёт»

🚀 Деньги в `double` — production-баг: `0.1+0.2 != 0.3` (двоичные дроби!).
Правила: создавать из СТРОК (`new BigDecimal("0.1")`, не из double!),
`equals` сравнивает и scale (`2.0` vs `2.00` — НЕ равны!), сравнивать —
`compareTo`, деление — только со scale+rounding (бесконечные дроби иначе
взрываются `ArithmeticException`), scale держать `setScale(2, HALF_UP`).

🔍 Где в проекте: ВСЕ финансы (`Company`, `FinanceService`, цены ракет);
`Quest21_MoneyTime`, задачи 1–5.

🪤 Ловушка: `new BigDecimal(0.1)` уже содержит двоичный мусор (0.1000000000000000055...).
Только строки!

🎤 *«Почему не double для денег?»*
<details><summary>Ответ</summary>
Двоичная плавающая точка не представляет десятичные дроби точно — копейки
плывут. BigDecimal — десятичная арифметика произвольной точности с явным
округлением. Цена — скорость, но для денег точность важнее.
</details>

## Date/Time вглубь: пояса, периоды, форматтеры — «мировые часы»

🚀 `LocalDate/Time/DateTime` — без пояса («время на борту»). `Instant` — точка
на шкале UTC. `ZonedDateTime` — момент + пояс (`ZoneId.of("Asia/Qyzylorda")` —
настоящий пояс Байконура!). `Duration` — точное время (полёты!),
`Period` — календарное (возрасты: месяц ≠ фиксированные часы!).
`DateTimeFormatter` с паттерном + `Locale` («4 октября 2026»),
`ChronoUnit.DAYS.between` для разниц.

🔍 Где в проекте: `Duration` полёта в `MissionResult`, `hireDate/foundedDate`,
ISO-строки в сейвах; `Quest21_MoneyTime`, задачи 6–9.

🪤 Ловушка: `Period` в днях между далёкими датами ≠ `ChronoUnit.DAYS`?
Нет — дни совпадут, а вот месяцы/годы Period считает календарно!

🎤 *«Duration vs Period?»*
<details><summary>Ответ</summary>
Duration — точная длительность (секунды/наносекунды, часы полёта).
Period — календарная (годы/месяцы/дни, возраст, подписка). Месяц — не
фиксированное число часов, поэтому Duration месяцами не меряет.
</details>

## File I/O — «чёрный ящик»

🚀 Сейв проекта — обычный текст: секции `[ROCKETS]`, `[MISSIONS]`, поля через `|`.
Его можно открыть в блокноте и даже править руками. Формат переживает добавление полей,
если парсер терпит их отсутствие (привет, LVL-41 в ROADMAP).

🔍 Где в проекте: `SaveLoadService` — `Path`/`Files`/`BufferedReader`/`BufferedWriter`,
`UTF_8` явно (зависимость от кодировки по умолчанию — баг переезда между ОС),

(`|` → `\p`, перевод строки → `\n`, `\` → `\\`) — иначе имя ракеты `A|B` развалило бы
структуру. Валидация заголовка + понятные ошибки вместо `ArrayIndexOutOfBounds`.

`InputReader` — вторая сторона I/O: цикл «спроси → прочитай → проверь → повтори»,
`Scanner` на `System.in` закрывается **один раз** в конце (закрыть раньше = убить
`System.in` навсегда).

🪤 Ловушка: `split("\\|")` по строке с экранированием — режет и внутри `\p`. Поэтому
в проекте свой посимвольный `split` с учётом `\`. (Переиспользуй это знание на LVL-40.)

🎤 *«Что такое try-with-resources? java.io vs java.nio?»*
<details><summary>Ответ</summary>
TWR автоматически закрывает AutoCloseable-ресурсы в обратном порядке открытия.
java.io — потоковый классический API; java.nio(.file) — Path/Files/каналы,
удобные хелперы (readString, walk, newBufferedWriter), лучше для нового кода.
</details>

## Многопоточность — «параллельные полёты»

🚀 Потоки делят кучу — и это как общий склад: два кладовщика, одновременно
списывающих топливо «прочитал-изменил-записал», потеряют одну запись (**race condition**).
Лекарства точечные, а не «побольше synchronized везде» (это убивает параллелизм и зовёт deadlock).

🔍 Где в проекте (`MissionService` + `Company` — маленький, но настоящий concurrency):
- `Executors.newFixedThreadPool(4)` — пул для фоновых полётов;
- `Callable + Future` (`launchAsync`, веерный `launchAllReady`), есть и `CompletableFuture`-вариант;
- `synchronized (mission)` — запрет двойного запуска **одной** миссии (разные миссии летят параллельно);
- `AtomicInteger` — счётчик полётов без блокировок;
- `synchronized deposit/withdraw` + `synchronizedList` историй — деньги и журнал общие для всех полётов;
- `ConcurrentHashMap` в репозиториях — чтение состояния без глобальных замков.

Правило проекта: блокируется **только** реально общее изменяемое место и **не более
одного монитора за раз** — поэтому deadlock'у взяться неоткуда.

🪤 Ловушка 1: `volatile` чинит **видимость**, но не атомарность `balance = balance - x`
(это всё ещё гонка). Ловушка 2: `Thread.sleep` в цикле вместо `Future.get()` —
костыль вместо синхронизации. Ловушка 3: забытый `shutdown()` пула — JVM не завершится,
тест повиснет (поэтому в тестах `@AfterEach → shutdown()`).

🎤 *«synchronized vs volatile? Что такое race condition и deadlock?»*
<details><summary>Ответ</summary>
synchronized — взаимное исключение + видимость; volatile — только видимость
(флаги остановки — ок, счётчики/аккумуляторы — нет). Race condition: результат зависит
от порядка выполнения потоков (потерянные обновления). Deadlock: потоки держат замки
и ждут чужие по кругу. Лечение: порядок захвата замков, минимум критических секций,
java.util.concurrent вместо ручных synchronized там, где есть готовое.
</details>

## Concurrency вглубь: жизнь потока, замки, пулы — «экипаж и вахты»

🚀 Жизнь: NEW → RUNNABLE → BLOCKED/WAITING → TERMINATED. `start` рождает,
`join` ждёт, `sleep` спит сам, `interrupt` — вежливая просьба (поток проверяет
флаг/ловит исключение; убить снаружи НЕЛЬЗЯ!). Два зла: невидимость (кеши —
лечит `volatile`/синхронизация) и неатомарность (`count++` = 3 операции!).
`volatile` — только видимость; `Atomic*` — видимость + атомарность (CAS);
`synchronized` — всё + mutual exclusion (монитор объекта, держать минимум!).
Пул: `submit(Callable)` → `Future` (`get` ждёт, `get(timeout)` с дедлайном);
пул гасить `shutdown()` (иначе JVM не завершится!). `ConcurrentHashMap` —
для общих карт (`merge/computeIfAbsent` атомарны!).

🔍 Где в проекте: `launchAllReady` (веер + сбор), `deposit/withdraw` (synchronized),
`completedFlights` (AtomicInteger), склады (ConcurrentHashMap); `Quest24`, задачи 1–3, 6, 8.

🪤 Ловушка: `get()` без таймаута на зависшей задаче — висишь вместе с ней.
И негашеный пул в тесте — висящий билд!

🎤 *«Чем synchronized отличается от volatile?»*
<details><summary>Ответ</summary>
synchronized: взаимное исключение + видимость (дороже, блокирует).
volatile: только видимость (флаги остановки — да, счётчики — нет!).
Счётчики — Atomic*, составные операции — synchronized/concurrent-структуры.
</details>

## Deadlock и CompletableFuture: клинч и цепочки — «узел и канат»

🚀 Deadlock: поток 1 держит A и ждёт B, поток 2 — наоборот. Условия: два+ замка,
разный порядок, ожидание без таймаута. Профилактика: ГЛОБАЛЬНЫЙ порядок замков
(все берут A→B), один замок вместо двух, `tryLock` с таймаутом.
CompletableFuture: `supplyAsync` → `thenApply` (преобразовать) →
`thenAccept` (потребить), ошибки — `exceptionally` (цепочка не рвётся молча!);
`thenCombine` сливает два future, `allOf` ждёт пачку (результаты — из исходных!).
`join()` ждёт (unchecked!), `get()` — checked.

🔍 Где в проекте: `launchAsyncCompletable` + `thenAccept` в `MissionsController`;
`Quest24`, задачи 4–5 (живой клинч на daemon-потоках!) и 7.

🪤 Ловушка: дедлок чинить «слипами» — маскировка, а не лечение. Лечится только
порядком/устранением замков. И дебаг дедлока — `jstack`/дамп потоков!

🎤 *«Как найти причину deadlock?»*
<details><summary>Ответ</summary>
Thread dump (jstack, IDE): ищем циклы «ждёт замок, который держит другой».
Видим схему «держит A, ждёт B» ↔ «держит B, ждёт A» — чиним единым порядком
захвата или убираем один из замков.
</details>

## Сборщик мусора — «уборка отсеков»

🚀 В Java память не освобождают руками — этим занимается GC по принципу
**достижимости**: нет пути от живых корней (стек, static) до объекта — значит, мусор.
Молодые объекты умирают в Eden (minor GC, быстро), долгожители переезжают в Old
(major GC, реже и дороже).

🔍 Где в проекте: кода про GC нет — и это правильно, его не вызывают из прикладного кода.
Короткоживущие (`EventContext`, стримы, билдеры логов) умирают молодыми и почти бесплатно.
Долгоживущие (`Company`, репозитории в `Application`) один раз переезжают в Old и живут.
Immutable (`Transaction`, `MissionResult`) не плодят мусор от защитных копий.
А `try-with-resources` закрывает **ресурсы** (файлы) — это не GC, GC файлы не закрывает!

🪤 Ловушка: «утечка памяти в Java невозможна» — возможна, как **непреднамеренно достижимые**
объекты: статический кеш без чистки, забытые слушатели, `ThreadLocal` без `remove()`.
Симптом: `OutOfMemoryError` при «вроде бы» пустых ссылках — копай, кто держит.

🎤 *«Как работает GC на пальцах? Что такое утечка в Java?»*
<details><summary>Ответ</summary>
Reachability + поколения (Eden/Survivor/Old): большинство умирает молодым.
Утечка — объекты, которые больше не нужны, но достижимы (static-коллекции, слушатели,
кеши). Диагностика: heap dump + dominator tree, метрики GC-пауз.
</details>

## var — «сам догадайся, компилятор»

🚀 `var` — не `var` из JavaScript и не динамика: тип всё равно строгий, просто его
выводит компилятор из правой части. `var x = 10` — это `int`, навсегда. Удобно для
длинных generic-типов (`var grouped = ...collect(groupingBy...)`), мусор — когда тип
неочевиден (`var x = get()` — что там? кто знает...).

🔍 Где в проекте: `var` почти не используется — намеренно, чтобы типы были видны
новичку. На LVL 6Б ты сам найдёшь 3 места, где `var` уместен, и 3 — где вреден.

🪤 Ловушка: `var` нельзя без инициализатора (`var x;` — ошибка), нельзя для полей
класса и параметров методов, и `var x = null` не скомпилируется (выводить-то не из чего).

🎤 *«var — это dynamic typing?»*
<details><summary>Ответ</summary>
Нет, типизация остаётся статической: тип фиксируется при компиляции и проверяется
как обычно. <code>var</code> — только сокращение записи для локальных переменных.
Поля, параметры и возвращаемые типы — всегда явные.
</details>

## record — «данные без церемоний»

🚀 Бывают классы-«сущности» (ракета: состояние + поведение) и классы-«конверты»
(итог полёта: просто донести данные). Для конвертов писать геттеры/equals/toString
руками — бюрократия, поэтому есть `record`: одна строка объявляет поля, а компилятор
генерирует конструктор, геттеры, `equals/hashCode/toString`. И всё это — immutable.

🔍 Где в проекте: `MissionResult` — идеальный record: создали после полёта, прочитали,
положили в историю. Обрати внимание: компоненты называются `missionId()`, а не
`getMissionId()` — у рекордов свой стиль именования.

🪤 Ловушка: record — всегда `final` (наследоваться нельзя), поля — всегда `final`.
Нужна мутабельность или иерархия — это обычный класс, record не для этого.

🎤 *«Когда record, а когда класс?»*
<details><summary>Ответ</summary>
Record — прозрачный носитель неизменяемых данных (DTO, результаты, ключи, события).
Класс — состояние + поведение, изменяемость, наследование. Эвристика: если у класса
только конструктор, геттеры и equals — это record, который притворяется классом.
</details>

## Pattern matching для instanceof — «проверка с подарком»

🚀 Старый стиль: проверил `instanceof`, потом отдельно кастанул — две строки, два шанса
ошибиться. Новый стиль: `if (o instanceof Rocket other)` — проверка и готовая переменная
`other` нужного типа в одном движении. Компилятор сам доказывает, что каст безопасен.

🔍 Где в проекте: ВСЕ `equals`-методы (`Rocket`, `Employee`, `Mission`...) написаны
через паттерн: `if (!(o instanceof Rocket other)) return false;`. На LVL 16Б перепишешь
один из них в старом стиле — и почувствуешь разницу в три строки.

🪤 Ловушка: переменная паттерна видна только там, где проверка точно прошла
(в `if`-ветке — да, после `if (...) return false;` — тоже да, умный flow-анализ;
а вот в `else` при положительном условии — нет).

🎤 *«Что даёт pattern matching?»*
<details><summary>Ответ</summary>
Меньше шаблонного кода и целый класс ошибок каста исчезает: переменная уже нужного
типа, компилятор следит за областью видимости. Дальше та же идея растёт в
pattern matching для switch (превью в 17, финал в 21).
</details>

## Text blocks — «многострочность без плюсов»

🚀 Склейка длинного текста через `"..." + ... + "..."` с `\n` — лесенка боли.
Text block (`"""`) — пишешь текст как есть, с переносами и кавычками, отступ
подстраивается под закрывающие `"""`.

🔍 Где в проекте: меню печатают построчно через `println` — на LVL 11Б перепишешь
приветствие `Application` на text block и сравнишь читаемость. А формат сейва
(`SaveLoadService`) — пример обратного: там строки собирает код, а не литерал.

🪤 Ловушка: открывающие `"""` должны заканчиваться переводом строки (текст — со
следующей), а случайные пробелы в конце строк внутри блока — остаются в строке
и дают загадочные баги сравнений. IDE их обычно подсвечивает.

🎤 *«Чем text block лучше конкатенации?»*
<details><summary>Ответ</summary>
Читаемость многострочного текста (SQL, JSON, ASCII-арт, шаблоны), отсутствие экранирования
кавычек и `\n`. Не замена StringBuilder: блок — для фиксированного текста, билдер —
для сборки в цикле.
</details>

## Аннотации и рефлексия: откуда магия JUnit — «закулисье»

🚀 Аннотация — метка для инструментов: `@Override` проверяет компилятор,
`@Deprecated` предупреждает, `@Test` находит JUnit. Своя: `@interface` +
`@Retention(RUNTIME)` (иначе рефлексия слепа!) + элементы.
Рефлексия читает чужой класс: `Class<?>`, `getDeclaredMethods/Fields`,
`setAccessible` (взлом private!), `Method.invoke`. Так Surefire находит тесты,
а фреймворки — поля для инъекций. Цена: медленно, небезопасно по типам,
ломается при рефакторинге. В проде — скупо, в тулах — нормально.

🔍 Где в проекте: `Quest23_Reflect` — своя `@Critical` + чтение/вызов;
в проде аннотации — `@Override` везде, `@FunctionalInterface` в `ui`.

🪤 Ловушка: `@Retention` по умолчанию — CLASS (в рантайме НЕ ВИДНА!).
Забыл RUNTIME — рефлексия метку не найдёт, молча.

🎤 *«Как JUnit находит тесты?»*
<details><summary>Ответ</summary>
Рефлексией: сканирует классы, ищет методы с `@Test` (RUNTIME-аннотация),
создаёт экземпляр, вызывает метод, ловит assertion-ошибки как падения.
Магии нет — есть `Class.getDeclaredMethods()` + `isAnnotationPresent`.
</details>

## JUnit 5 как инструмент: AAA, lifecycle, параметризация — «допрос с протоколом»

🚀 Структура AAA: Arrange (готовь) / Act (действуй) / Assert (проверяй) —
разделяй пустыми строками. Жизнь: конструктор → `@BeforeEach` → `@Test` →
`@AfterEach` (свежий экземпляр на КАЖДЫЙ тест!), тяжёлое — в `@BeforeAll` (static).
`assertAll` показывает ВСЕ падения разом; `assertThrows` ВОЗВРАЩАЕТ исключение
(проверяй сообщение!). Параметризация: `@ValueSource` (простые),
`@CsvSource` (таблички), `@MethodSource` (фабрика `Arguments`).
`@Nested` группирует тесты как документацию. Имена — предложения, не `test1`.

🔍 Где в проекте: `src/test` — 13 файлов-образцов: параметризация в
`ProbabilityCalculatorTest`, фикстуры в `TestFixtures`, границы везде.

🪤 Ловушка: тесты с общим изменяемым static-состоянием — порядок-зависимые
«мигающие» тесты. Изоляция: свежие фикстуры в `@BeforeEach`!

🎤 *«Зачем assertAll?»*
<details><summary>Ответ</summary>
Обычные asserts останавливаются на первом падении — остальные проверки не
выполняются. `assertAll` выполняет все и показывает все падения сразу:
один запуск — полная картина.
</details>

## Maven: фазы, скоупы, плагины — «конвейер сборки»

🚀 Жизнь: `validate → compile → test → package → verify → install → deploy`;
`clean` — отдельная (чистит `target`). Плагины привязаны к фазам (compiler→compile,
surefire→test, jar→package). Зависимости: `compile` (везде), `test` (только тесты —
наш JUnit!), остальное — по необходимости. `src/main` vs `src/test` — святое:
тестовый код не попадает в прод-jar (проверь: test-скоуп!). Артефакт: jar + `libs/`
для jpackage; запуск UI — `javafx:run` (нативки под текущую ОС сам подберёт).

🔍 Где в проекте: `pom.xml` — прочитай целиком (зависимости, плагины, mainClass
jar-манифеста vs javafx-плагина); скрипт `q` — сборка вне Maven (почему?).

🪤 Ловушка: убрал `test`-скоуп у JUnit — потащил тесты в прод. И `mvn test`
без `clean` после переименований — старые классы в `target` врут!

🎤 *«Что делает mvn clean test?»*
<details><summary>Ответ</summary>
`clean` удаляет `target`, затем lifecycle до `test`: validate → compile
(прод-классы) → test-compile → test (Surefire гоняет `*Test`). Зелёный —
значит, собралось и все тесты прошли.
</details>

## Debugging как навык: рентген программы — «медотсек»

🚀 Арсенал: breakpoint → Step Over (шаг, не заходя) / Into (зайти) / Out (выйти);
watches (следи за выражением); Evaluate Expression (выполни код на паузе —
вызови геттер! поменяй поле! осторожно, меняет состояние); stack frames
(прыгай вверх, смотри локалки вызывателей); conditional breakpoint (пауза
по условию); exception breakpoint (пауза на первом NPE!). Чтение stacktrace:
сверху вниз — исключение, СВОЙ первый фрейм (номер строки!), потом чужие.

🔍 Где в проекте: `flyMission` — идеальный пациент (ветвления+состояния);
`Quest25_BugHunt` — 6 живых багов чинить ТОЛЬКО дебагером (LVL 64!).

🪤 Ловушка: дебаг принтами вместо точек — медленно и засоряет код.
Принт отладил — удали! А лучше сразу breakpoint.

🎤 *«Как найти место падения по stacktrace?»*
<details><summary>Ответ</summary>
Читаем сверху: тип + сообщение исключения, затем первый фрейм СВОЕГО кода
(пакет проекта!) с номером строки — туда и ставим breakpoint. Дальше вниз —
чужие фреймы (библиотеки), они для контекста.
</details>

## Чистый код и SOLID-лайт: практика без проповедей — «устав порядка»

🚀 Имена не врут (`findReady` — возвращает готовых, а не всех!); методы короткие;
SRP — одна причина меняться; DRY — правило трёх (два повтора — терпим, три —
выносим); magic numbers — в константы; early return против вложенности;
`Objects.requireNonNull` на входах (fail-fast вместо NPE в глубине!).
SOLID-лайт на проекте: S — сервисы про своё; O — новые события без правок;
L — наследники `Employee` взаимозаменяемы; I — узкие репозитории;
D — зависимости от интерфейсов (`Repository`), а не от `InMemory`!

🔍 Где в проекте: везде понемногу; LVL 45Д — найти 3 нарушения и исправить;
LVL 52Б — ревью своего кода по чеклисту.

🪤 Ловушка: «чистый код» как самоцель (абстракции ради абстракций) — хуже грязи.
Правило: код должен стать ПРОЩЕ читать, иначе рефакторинг вреден.

🎤 *«Что такое D в SOLID?»*
<details><summary>Ответ</summary>
Dependency Inversion: модули зависят от абстракций, а не от деталей.
У нас: сервисы берут `RocketRepository` (интерфейс) через конструктор —
InMemory подменяется, сервисы не меняются. Внедрение через конструктор —
самый честный DI без фреймворков.
</details>

## Modern Java: switch-выражения и sealed — «новый флот»

🚀 Switch-выражение возвращает значение (`->` + `yield` для блоков),
исчерпываемость проверяет компилятор (добавил enum — switch без default
не скомпилируется!). `sealed` классы: наследники — только из разрешённого
списка (`permits`) — иерархия под контролем (идеально для Result/состояний!).
Правило курса: модерн — приправа, не замена: сначала фундамент
(циклы, equals, коллекции), потом сахар.

🔍 Где в проекте: switch-выражения — в меню и валидаторе (`case READY ->`),
`record` — `MissionResult`, pattern matching — все `equals`.

🪤 Ловушка: гнаться за модным синтаксисом вместо читаемости.
`var` там, где тип неочевиден, — уже не модерн, а вред.

🎤 *«Чем switch-выражение лучше оператора?»*
<details><summary>Ответ</summary>
Возвращает значение (нет забытых присвоений в ветках), стрелки без fall-through
(нет забытых `break`), компилятор проверяет исчерпываемость по enum/sealed —
новую ветку нельзя «забыть».
</details>
